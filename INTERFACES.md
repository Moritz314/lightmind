# Interfaces (contract for parallel builders)

Rule zero: `model.py` and `files.py` are the shared base. Change them only via the coordinator, and additions to `model.py` only in a backward compatible way.
Stubs raise `NotImplementedError`; keep every public signature and docstring semantics. Add private helpers freely.
Import direction (arrows = "may import"): `cli` -> everything; `loop` -> context, tools, runs, hooks, providers.base (and `rules`, `secrets` late, inside functions); `hooks` -> tools, providers.base, files (`loop.Session` only as a type); `tools` -> rules, secrets, runs; `providers.*` -> secrets, tools (claude_sdk only; it also imports `rules` late, for the PreToolUse guard); `rules`, `secrets`, `context`, `runs` -> `files`, `model` only. No cycles.

## Principles (binding)
- **Markdown is the configuration.** No folder name, permission, limit or restriction in Python. Settings live in the frontmatter of `templates/lightmind.md`, rules in `templates/permissions.md`, accounts and prices in `templates/providers/*.md`. Code reads and applies.
- **Smallest core:** AI input (providers), chat start (context + loop), tool execution, rule check from files, secret injection, run log. Nothing else in phase 1.
- Names in Python tests/fixtures come from the template tree, never from literals in modules.

## Home and paths (`files.py`)
The core knows exactly one file name: `lightmind.md` at the tree root (root = `--home` > `$LIGHTMIND_HOME` > `~/lightmind`; `Home.resolve_root`). Its frontmatter is `home.settings` (never sent to the AI), its body is the master prompt. The sections of the frontmatter are listed under "Tree". `home.settings`, `home.paths`, `home.files`, `home.defaults` read the current file through the mtime cache: an edit is seen by the next call. Home's own lookups use the cached document directly, so replacing the public name `settings` (a test double) does not break path resolution.

Use only:
- locations: `home.path("agents")` (absolute `Path`; `~` and the placeholders `{os}`, `{arch}` are expanded), `home.rel("agents")` (as written, no trailing slash), `home.filename("tool")`, `home.abs(rel)`. A missing key raises `PathsError`; there are no fallbacks in code. Renaming a folder = edit `lightmind.md` (and any rule pattern in `permissions.md` that names it); nothing else. `rules` refuses a `paths` entry that leaves the tree root, so a vault outside the tree needs a changed check there.
- documents: `home.doc(rel)` (mtime-cached `Doc`), `home.key_doc("permissions")` (a `paths` key that names a file; a name without a `paths` entry that is a mapping in the frontmatter, such as `context`, gives that section as `Doc.meta`), `home.rows(key)`.
- prompt: `home.master_prompt()` = the body with placeholders filled, byte-stable; `home.fill(text, extra=None, absolute=False)` (`{key}` = `paths.key` as written, or absolute; `{file_key}` = `files.key`; `{home}`, `{os}`, `{arch}`; unknown placeholders stay).
- `home.ui_rows("start_menu" | "slash") -> [[cells]]`.
- environment: `home.runtime_env(base=None)` = a copy of `os.environ` with UV_CACHE_DIR, UV_PYTHON_INSTALL_DIR and PLAYWRIGHT_BROWSERS_PATH pointing into the tree (`cache`, `python`, `browsers` locations) and the `bin` location at the END of PATH (a file an agent leaves there cannot shadow a system program; the bundled uv serves only where the system has none). Everything the core starts (hooks, the bash tool, tool scripts) should begin with it, so uv never touches a cache outside the tree. `files.platform_tag() -> (os, arch)`.

Loaders. A name starting with `_` or `.` and the README are never items. Agents, workflows, triggers, servers and projects are listed by name: `list_agents()` / `load_agent(name) -> Agent`, `list_triggers()` / `load_trigger(name) -> Trigger`, `list_servers()` / `load_server(name) -> Server`, `list_projects()` / `load_project(name) -> Project` / `has_project(name) -> bool` (a valid name, `a-z0-9-`, and the folder is there). `Agent.project` is the agent's `project:` (its default project, a folder name; empty = none). Skills and tools are listed as objects: `list_skills()`, `list_tools()` / `load_tool(name)`. `load_providers() -> ProvidersConfig` and `prices(account=None) -> {model: (input, output, cache_write, cache_read)}` read `providers/*.md`.

Other helpers: `parse_frontmatter`, `parse_rows` (`# Section` + `- a | b | c`, ` #` comments), `split_arrow`, `parse_size`.

## Drop-in tools and skills
- **No registration.** A folder dropped into the `tools` / `skills` location is found at the next chat start (loaders list the folder fresh; mtime cache only avoids re-parsing).
- **Tool** = folder with a script and a `README.md` (what it does, the exact command line, what it prints). Python scripts declare dependencies with **PEP 723 inline metadata** (`# /// script` block) and run with `uv run`, so dependencies are fetched on first use into the tree's own cache. Tools are not function calls by default: the AI runs them with the bash tool as the skill or the README says (`tools.as_functions: false` in `lightmind.md`). `tool.md` is an optional manifest (frontmatter `name`, `description`, `run`, `params`, `category`, `match`, `secrets`, `timeout`, `output`, `server`); `load_tool` reads it first, else the README (frontmatter, or its first paragraph as the description) and `Tool.run` stays empty. With `tools.as_functions: true` a tool that has a manifest is also offered as a function (params as JSON on stdin); register no function for a tool whose `run` is empty. Examples: `templates/tools/_example/`, `templates/tools/vault/`.
- **Skill** = `<name>.md`, or a folder with `skill.md` or **`SKILL.md`** (Claude Code format, accepted unchanged; frontmatter `name`, `description`; optional `scripts/`, `references/` next to it). Existing skills can be copied in as-is. Extra Lightmind keys (`preload_when`, `requires`, `secret`) are optional.
- The shipped `permissions.md` has no `new-tool(*)` rule (normally open); a user may add one, the hash store lives in the `state` location.

## Tree (what `lm init` creates; `templates/`)
The shape of concept.md plus `tools/`. Every folder has an explaining `README.md` (for the user and for the AI: purpose, format, use, how to create an item); an example is named with a leading underscore, which no loader lists. The master prompt tells the AI to read a folder's README before it creates or changes anything there.

```text
lightmind/
├─ lightmind.md      frontmatter = every core setting (never sent), body = master prompt (always sent first)
├─ permissions.md    base rules, grant_files, money_limit, audit; never sent
├─ rechte.md         the numbered rights the modes switch
├─ modes/            one file per mode (auto, plan, bypass); its text is sent
├─ config.md         the settings the user changes (defaults, sessions.open, ui.boot, ui.boot_wait, run.max_parallel, run.max_depth, vscode.agent/model/effort/mode, quick.model/effort/context/mode); wins over lightmind.md, see config.md below
├─ .gitignore        template file dot-gitignore (the only dotfile at the root)
├─ skills/           README.md, _example/SKILL.md
├─ tools/            README.md, _example/ (example.py, README.md), vault/ (status.py, README.md)
├─ agents/           README.md, _example/ (agentMaster.md, tools.md)
├─ workflows/        README.md, lib.py (helpers for scripts), _example/ (agentMaster.md, tools.md, workflow.py)
├─ triggers/         README.md, _example.md
├─ servers/          README.md, laptop/info.md (host: local, the default), _example/info.md
├─ projects/         README.md, _example/ (projectMemory.md, projectAssets.md, tools.md)
├─ vault/            README.md (the vault itself is paths.vault, by default this folder)
├─ secrets/          README.md, _example/info.md (never a .env)
├─ runs/             README.md (one folder per run, written by the core)
├─ providers/        README.md, claude-abo.md, _example-anthropic-api.md, _example-openrouter.md
└─ system/           the technical engine, one visible folder: README.md, lm, lm.cmd, state/ (runtime, python, cache, bin, claude, browsers appear on first start)
```

### config.md (the settings page; `files.py`, `settings.py`, `init.py`)
`config.md` sits at the tree root (`paths.config`, default `config.md`; the default is the constant `files.CONFIG`). Its frontmatter holds the settings the user changes, each with a short comment and its allowed values; the text below is a guide and is never sent. **The core reads a fixed list of keys only** (`files.CONFIG_KEYS`): `defaults.provider|model|effort|context|mode` (NOT `defaults.server`: that is per machine and lives in `<state>/local.md`), `sessions.open` (`tab` | `window` | `replace`, default `tab`), `ui.boot`, `ui.boot_wait`, `run.max_parallel`, `run.max_depth`, `quick.model|effort|context|mode` (`quick.permission_mode` is read as an alias of `mode`) (the quick chat `lm q`; a missing section or key, in an older tree, means the built-in value `opus|high|500k|bypass`, see `quick.py`). Everything else in the file is ignored. `run.ask_channel` stays in lightmind.md, money limits in permissions.md, there is no `sync:` section.
- **Layers, later wins** (`Home._meta`, so `Home.settings`, `Home.defaults` ... show the result): code defaults < lightmind.md < config.md < `<state>/local.md`. A key that is set but empty in config.md counts as not set. `Home.config -> ConfigFile(path, state, error, values, ignored, both)` with `state` = missing | empty (blank file) | ok | error | unguarded, cached by size and time of config.md and permissions.md and by the identity of the lightmind.md document; `Home.config_file`; `Home.forget(path)` drops the cached readings after the core wrote a file (the cache cannot see an edit of the same size within one clock tick; `settings.save` calls it). A broken config.md (YAML error, no frontmatter) is `error`: its values are NOT used, lightmind.md applies and `lm check` and the boot list say FAIL with the line. **Fail closed:** a config.md with content counts only while `Home.unguarded_reason()` is empty; else its state is `unguarded` (`error` = the reason) and its values are NOT used either (lightmind.md applies), because `defaults.mode: bypass` there would otherwise be a mode an agent could set. Without a config.md, or with a blank one, everything behaves as before: old trees run on.
- **`lm check` and the boot checklist** (group `config`): FAIL a broken file; FAIL when permissions.md does not guard it (names the reason, says what is not used, and `Run lm update`); WARN keys the core does not read (named); INFO a key set in lightmind.md and in config.md (config.md wins); INFO missing or empty (`lm update` fills it).
- **Guard.** The shipped permissions.md lists `write({config})` in `grant_files`, right behind `write({entry})`: a locked ask in the mode auto; the mode bypass carries the whole list as a locked deny instead, because `defaults.mode: bypass` there removes every question for the next chat. `rules._home_vars` knows `{config}` even where lightmind.md has no `paths.config`. **`Home.unguarded_reason() -> str`** ('' = guarded) asks the rule checker itself, not the text: for every mode of permissions.md, `write` and `edit` of the config path (`rules.build_layers` with no agent and no session, `decide_all`) must come out `ask` or `deny`; an `allow` names the mode, and whatever cannot be judged (no permissions.md, no mode, a rule error) counts as unguarded. While it runs `Home.config` reads as missing (no loop). The verdict is cached with `permissions.md` (size and time) and the lightmind.md settings; the first one costs about 50 to 100 ms per process (`rules.real_memo()` lets its 6 decisions share the `realpath` results; only that block, never a running chat). `init.config_guarded(home)` is `not home.unguarded_reason()`.
- **Older trees: `init.migrate_config(home, create=False, repair=False) -> [notes]`**, run by `update_tree` (`repair=True`) and by `cli._migrate` when a person starts the TUI (top level only: never with `LM_DEPTH` above 0 or `LM_RUN` set, an agent does not do this). (1) `protect_config` (only while `unguarded_reason` is set; `lm update` does it every time the guard is missing, the TUI start only for a config.md that is about to be filled, so a line the user took out is not put back behind their back) inserts `- write({config})` behind `write({entry})` (else `write({permissions})`) in `grant_files`, proved by parsing again (the aliases of the list follow), the old file stays as `permissions.md.bak-<date>`; a tree without such a line, or whose modes still let the write through, gets a note instead, and no fill happens while `config_guarded` is false. When the file already held settings (not in effect until now) a second note names them: they apply from now on. `templates.json` has `version` and `shipped` only. (2) `fill_config` fills an EMPTY config.md (a missing one too, when `update_tree` finds it was never shipped) with the template and the values of `entry.meta` of lightmind.md (not of the local.md overlay), which are MOVED: written to config.md and removed from lightmind.md (`settings.drop_keys`: inline comments go with their lines, a section left empty goes with the comment lines above it, one comment line says where the settings went), the old file stays as `lightmind.md.bak-<date>`. `defaults.server` goes to `<state>/local.md` (created, or the key added; a value already in local.md wins; a local.md without frontmatter keeps the server in lightmind.md and says so). Everything is built and proved in memory first and nothing is written when a step fails (note `config.md: not filled, nothing was changed`); the writes go local.md, config.md, lightmind.md, so a crash in between loses nothing (both files then hold the value, config.md wins). `update_tree` returns `Created` (a list; `.notes` = what migrate did), `lm update` prints the notes and `--json` adds `notes` when there are some. Tests: `tests/test_config.py`.
- **`settings.py`** (imports `files`) is the only way a settings file is changed, for the core and for both screens. `edit_text(text, {("defaults", "model"): "opus", ...}, after=())` makes every change on its own line: the value comes from `yaml.safe_dump` (one line, quotes only where needed), an inline comment stays and keeps its column when the room allows, a value that is already so is left as written; a missing key is inserted (top-level: behind the first of `after` that exists, else after the last line of the frontmatter; nested: behind the last line of its section; a missing section is added at the end); `None` removes a key. A value over several lines, a section in flow style or a layout it cannot read is a `SettingsError`, never a guess. **Counter-check (`prove_text`):** the result is parsed again (`front_meta`: strict YAML) and must equal "old plus the changes", types included (`True` is not `1`), and the text below the frontmatter must be identical, else `SettingsError` and nothing is returned or written. CRLF and a BOM stay (each line keeps its own ending, inserted lines follow their neighbour). `drop_keys(text, [(section, key)], note)` removes keys the same way. `save(home, path, changes, loaded=None, after=())` reads the file again, raises `Conflict` when it differs from `loaded` (the bytes a screen showed), proves, writes atomically (temp file, `os.replace`; `SettingsError` when the file is locked) and calls `home.forget(path)`; `backup(path)` makes `<name>.bak-<date>` (`-2`, `-3` ... never overwriting). Tests: `tests/test_settings.py`.
- **The settings page (`settings.py`, the same module for the TUI screen and the later HTML page; neither has a field list of its own).** `GENERAL` (the fourteen fields of config.md, the last four `vscode.agent/model/effort/mode` and the four `quick.model/effort/context/mode` with an `unset` row (= the built-in value): `defaults.provider/model/effort/context/mode`, `sessions.open`, `ui.boot`, `ui.boot_wait`, `run.max_parallel`, `run.max_depth`; `defaults.server` is local.md's and not there) and `AGENT` (`provider`, `model`, `effort`, `mode`, `project` of an agent file; each may be unset) are tuples of `Field(path, label, kind, help, low, high, unset, danger)`. `area_of(field)` says which page of the TUI screen a general field is on: the `workflow.*` fields are the page "Ultracode", the rest "General". `options(home, field, values=None) -> [(value, label, note)]` is what a screen offers: accounts of `providers/`, the models and tiers of the chosen account (`values` says which), `EFFORTS`, `ui.context_sizes` or `CONTEXTS`, the modes of permissions.md, `tab|window|replace`, `true|brief|false`, whole numbers (`max_parallel` 1 to 32, `max_depth` 0 to 10), the folders of `projects/` (never `_` examples); a field with `unset` starts with `(None, wording)`; a value the file holds that the list does not know stays choosable. `check_value(home, field, value, values=None) -> str` is '' or why not: types are strict (`1` is not `True`), a plain model name an account does not list is still accepted, nothing is allowed that is not on the list. `read_general(home)`, `read_agent(home, name)`, `agent_names(home)`, `agent_file(home, name)` give a `Page(title, path, loaded, rows, scope, name, error, state)`; a `Row` is `(field, value, effective)` (`value` None = not set in the file, `effective` = what applies, the tree's default for an unset agent field); an empty or broken file is `Page.error` with no rows, never an exception; `Page.state` is how the core reads config.md (`ok|unguarded|error|missing|empty`). `save_page(home, page, changes) -> Page` checks every value first (`check_value` against what the other fields will be), drops what is already so, writes only the changed lines through `save` (so `Conflict` when the file changed since the page was read, the counter-check applies, CRLF/BOM stay) and returns the page read again; on any error nothing is written. An agent field set to `None` keeps its key with an empty value (the comment next to it stays), a key the file lacks is not added; a missing agent key is inserted behind `mode`, `effort`, `model`, `provider`, `description` or `name`, the first that exists. Tests: `tests/test_settings_page.py`.

### Portable layout of `system/`
The root of the tree holds only what matters to the user: `lightmind.md`, `permissions.md` and the content folders (plus the template `.gitignore`). Everything technical is ONE visible folder, `system/` (`paths.system`). The tree is self-contained: runtime, caches and logins live in that folder, nothing outside it.

```text
system/                          paths.system: the whole engine; git-ignored except the launchers and README; `lm` rebuilds the runtime when `runtimes/` is deleted
├─ README.md                     template: "technical engine, you never need to touch this; delete the runtimes folder to rebuild the engine; claude/ and state/ hold logins and state"
├─ lm, lm.cmd                    launchers (templates, with the bootstrap, see below); lightmind(.cmd) = lm, lmq(.cmd) = `lm q`, lmr(.cmd) = `lm resume` (one-line templates that call the lm next to them; `update_tree` brings them to older trees like any new template, an existing file stays)
├─ state/                        paths.state: templates.json (record of shipped template files), install-source.txt (one line, see init.py), ledger.jsonl, tools-approved.json, prompt files, limits, locks, tokens
├─ runtimes/<os>-<arch>/rN/       paths.runtime = runtimes/<os>-<arch>/: one venv with lightmind per build, several side by side (os = windows|linux|macos, arch = x86_64|arm64); `runtimes/<os>-<arch>.current` = one line, the name of the build new starts use; `runtime-<os>-<arch>/` is the single runtime of earlier launchers (legacy)
├─ (in each rN) lm-root.txt, lm-stamp.txt, lm-use.lock   the tree path (last step of a build), the stamp it was built for, the flock file of POSIX
├─ python/                       paths.python: UV_PYTHON_INSTALL_DIR
├─ cache/                        paths.cache: UV_CACHE_DIR, also the dependencies of tool scripts (PEP 723)
├─ bin/                          paths.bin: the uv binary (UV_TOOL_BIN_DIR too), LAST on PATH
├─ wheels/                       the kept lightmind wheel: a copied or moved tree rebuilds from it, offline
├─ uv-tools-<os>-<arch>/         UV_TOOL_DIR (the launcher's alone; no paths key yet)
├─ claude/<account>/             paths.claude: CLAUDE_CONFIG_DIR of a claude-subscription account (the portable login)
└─ browsers/                     paths.browsers: PLAYWRIGHT_BROWSERS_PATH
```

The launchers sit in `system/` and take its parent folder as the tree root (`LIGHTMIND_HOME`); they and `Home.runtime_env()` set the same variables, and `{os}` and `{arch}` are normalised the same way everywhere (`files.platform_tag()`, `uname`, `PROCESSOR_ARCHITECTURE`). A launcher knows the locations by their shipped names: renaming a `paths` key of the engine means editing the launcher too. `.gitignore` ignores `system/*` except `system/lm`, `system/lm.cmd` and `system/README.md` (so a git copy can start itself), `runs/*` except its README, and `secrets/**/*.env`; a git clone of a tree therefore has no engine, the launcher builds it, and `update_tree` restores a missing record (see init.py). `permissions.md` locks the whole folder for the AI (read, write, edit), so the Claude logins, tokens, ledger and runtime stay out of reach. `.gitattributes` of the repo keeps `system/lm` on LF and `system/lm.cmd` on CRLF (`lm.cmd` is pure ASCII).

**Bootstrap (`lm.cmd`, `lm`).** Environment set on every start: LIGHTMIND_HOME, UV_CACHE_DIR, UV_PYTHON_INSTALL_DIR, UV_TOOL_DIR (`system/uv-tools-<os>-<arch>`, not yet in `Home.runtime_env()` or `paths:`), UV_TOOL_BIN_DIR (= `bin`), PLAYWRIGHT_BROWSERS_PATH, UV_PYTHON_INSTALL_BIN=0 and UV_PYTHON_INSTALL_REGISTRY=0 (an explicit `uv python install` would otherwise write `python3.12.exe` into `~/.local/bin` and a key into the user registry, both verified), PYTHONHOME and PYTHONPATH cleared, `bin` appended LAST to PATH (a file left there cannot shadow a system program; the launcher calls its uv by full path). The Windows launcher runs in `setlocal`, so the caller's shell is not changed. Overrides: `LM_UV` (another uv program), `LM_PYTHON` (default 3.12).
- **Fast path:** the pointer `runtimes/<os>-<arch>.current` names `rN`; `rN/Scripts/lm.exe` (`bin/lm` on POSIX), the marker `lm-root.txt` of this tree and a `lm-stamp.txt` equal to `state/runtime-stamp.txt` exist: exec the runtime with all arguments, the exit code passes through. uv is not started (a missing `bin/uv` is only restored by copy or download). Without a pointer the legacy `runtime-<os>-<arch>/` is looked at the same way (a missing marker there means "outdated by an old lm update": it runs, but a new build is made).
- **Marker and stamp:** `rN/lm-root.txt` holds the tree path (one line, in the console code page on Windows, UTF-8 under sh); a moved or copied tree finds another path and builds a new runtime. It is the last step of a build (before only the pointer), so an interrupted build is never used. `rN/lm-stamp.txt` holds the content of `state/runtime-stamp.txt` at build start (empty when the file did not exist). **A new version is pending when the two differ**: `lm update` (and `--from`) write a fresh token (`runtime.request_rebuild`) and touch no runtime. A file instead of a name in the file name keeps long tree paths away from MAX_PATH. `install-source.txt` is UTF-8; `lm.cmd` reads it through PowerShell so a path with umlauts survives the OEM code page.
- **uv:** `bin/uv(.exe)` (+ `uvx`): a copy of the uv found on PATH (checked with `--version`), else the official installer with UV_UNMANAGED_INSTALL=`bin` (no PATH change, no profile, no receipt in `%LOCALAPPDATA%`; UV_INSTALL_DIR and UV_NO_MODIFY_PATH set too for older installers).
- **Build:** `uv python install 3.12`, `uv venv --python 3.12 --managed-python runtimes/<os>-<arch>/rN` (N = highest number in the folder + 1), `uv pip install --python <venv python> <wheel>[tui]` (the `tui` extra is Orbit's `textual`). The package: a wheel kept in `wheels/` wins (installed `--offline` first, quietly, then online); else `state/install-source.txt`, one line `KIND SPEC`: `folder <path>` (`uv build --wheel` into `wheels/`), `wheel <path>` (copied into `wheels/`), `requirement <PEP 508>` (passed on as it is). Messages go to stderr, stdout stays clean for pipes. A failure drops the partial `rN` and leaves the pointer alone, so the next start tries again.
- **Side by side, never replaced:** a build goes into a new `rN`; the pointer is written to `<pointer>.tmp` and moved over the old one (one step for every reader) only after `lm-root.txt` is written. No runtime in use is ever renamed, written or deleted by a build. `system/lm build` (`lm.cmd build`) only prepares the runtime and starts nothing (exit 0 when it is current or was built, 1 when it failed); `lm update` calls it at its end. One build at a time: `system/build.lock` (POSIX: a folder holding the owner's pid, a dead owner's lock is taken over; Windows: a file held open during the build, released by the system when the window dies). A start that finds a build running and has a usable runtime (even an outdated one) runs it and says "a new version is being built in another lm window"; without any usable runtime it waits up to `LM_LOCK_WAIT` seconds (default 300), as does `build`.
- **Cleaning up:** after every build and at every start that finds a folder besides the one that runs, the launcher tries the build lock once (silent when busy) and removes each runtime folder that is not the one it runs, not the one the pointer names and not in use. Windows: renaming the folder to `rN.drop` fails while `lm.exe`, `python.exe` or the bundled `claude.exe` run from it; that is the proof of use (a `.drop` folder is deleted, and again at the next start if a file held it). POSIX: every start holds a shared `flock` on `rN/lm-use.lock` (file descriptor 9, inherited by the exec'd lm; `runtime.hold()` does the same inside every lm process, so detached runs count); cleanup takes the lock exclusive and non-blocking first and deletes the folder while holding it. Without the `flock` program old builds are kept. The legacy `runtime-<os>-<arch>/` held no lock: it is removed when a pointed build exists and no process line names a file below it (`ps -A -ww`, else `/proc`); when the process list cannot be read it stays. Builds without a marker (a killed build) are removed under the lock.
- **`lm path`**, handled by the launcher before Python: Windows adds `system` to the USER Path in `HKCU\Environment` (the registry value, not setx: no duplicates by expanded, case-insensitive comparison, the value type REG_EXPAND_SZ is kept, then the environment change is broadcast); `LM_PATH_REGKEY` names another key below HKCU for tests. POSIX prints `export PATH="<system>:$PATH"` and writes no file.
- Measured (Windows 11, uv 0.12.1): first start 86 s (Python 15 s, packages 32 s), second start 0.8 s, moved tree rebuilt offline 8 s; `system/` 513 MB on disk (837 MB as Explorer adds hard links). Tests: `tests/test_launcher.py` (fake uv, also the POSIX launcher under Git's sh) and `tests/test_install.py` (`-m install`).

### Hooks (`on_start`, `on_prompt`, `on_end`)
Lists in the frontmatter; the runner is `hooks.py` (`run_on_start`, `run_on_prompt`, `run_on_end`, also importable from `loop`, see "Session API"). Zero tokens, no model. `on_start` runs before the first model call of a session, `on_prompt` before every message of the user, `on_end` after the last model call.
- Entry: a string (the command) or a mapping with `run`, `show`, `context`, `timeout` (15 s), `max` (8000 characters of context), `env`. `{key}` (the keys of `paths:`) is filled into `run` as written and into the values of `env` as absolute paths. The command starts in the tree root, in the shell of `shell:`, reads Claude Code compatible JSON on stdin (`hook_event_name` = SessionStart | UserPromptSubmit | SessionEnd, `session_id`, `cwd`, `transcript_path`, `prompt`), finds `CLAUDE_PROJECT_DIR` in its environment, and prints plain text or Claude Code's JSON (`hookSpecificOutput.additionalContext`, `systemMessage`). Claude Code hook scripts therefore run unchanged.
- `show` prints the output to the user. `context` hands it to the AI: the `on_start` outputs go to `build_context(state_info={"start": ...})` (state block, after the cache line); the `on_prompt` outputs are appended to that user message as a pointer. A failing command is a warning, never an error.
- The runner starts from `home.runtime_env()`, so `uv run` uses the tree's own cache.
- Shipped: `on_start` runs `uv run {tools}/vault/status.py "{vault}"` with `show` and `context` (one line about the vault); `on_prompt` and `on_end` are empty, with a commented example for a Claude Code hook script.
- lightmind.md is writable by agents, so a write to it asks the user (see permissions below); `session.hook_gate` is the second line.

### tools.md (agents, workflows, projects)
Sections `# Skills`, `# Tools`, `# Secrets`, `# Servers` (also `# Connectors`) with `- name` rows; a comma list (`- bash, files`) and `- name: detail` are accepted. Skills and tools become `Agent.tools` / `Project.tools`; an agent without `tools.md` has no loadout and sees everything. Listing is granting: a secret (`service/account`, or a bare `service` for all its accounts) and a server are kept in `Agent.secrets` / `.servers` and merged into `permissions["secrets"]` / `["servers"]`, which `rules.agent_layer` expands into allow rules. Only plain names count (letters, digits, `.`, `_`, `-`; no glob, no `..`): any other row is skipped with a `UserWarning` and grants nothing, never a wider grant. A project's `tools.md` does the same for `Project.permissions` (pass it as `project_permissions` to `rules.build_layers`); it is the ONLY source of project grants. A `permissions:` block in `projectMemory.md` is dropped with a `UserWarning` (that file is not protected, an agent may write it), and project-level allow/ask/deny rules no longer exist.

### providers/*.md
One file per account. Frontmatter: `type`, `config_dir`, `secret`, `admin_secret`, `base_url`, `server`, `use`, `models` (model -> input, output, cache_write, cache_read, USD per million tokens), `default_model`, `tiers` (tier -> model of this account), `fallback` (accounts), `alias`, `switch_at`. `load_providers()` gives `ProvidersConfig(default = defaults.provider, accounts, aliases = {alias: account}, fallback = {account: [...]}, tiers = {tier: {account: model}}, switch_at = the default account's or 0.9)`; resolve a tier with `Account.tiers`. `Home.prices()` feeds `runs.load_prices`. `claude-abo` has `config_dir: system/claude/claude-abo` (relative to the tree: `home.abs(account.config_dir)` is the CLAUDE_CONFIG_DIR) and no secret; API accounts name a secret that only the core reads (`secrets.reserved_refs`). A provider file ties a secret to an endpoint, so writing one asks the user.

**Several accounts of one type side by side** (for example two subscriptions, two API keys): each account is its own file. Subscriptions are separated by `config_dir` (own `CLAUDE_CONFIG_DIR` per turn, own login, own `{state}/limits-<account>.json`); API accounts by `secret:` (`anthropic/api-1`, `anthropic/api-2`; each provider call reads only its own key). `fallback:` chains link by link (`abo -> abo-2 -> api-1 -> api-2`, each file lists its successors); `loop._fallback` skips an account that cannot run (`accounts.account_status` state `login-missing` or `key-missing`). ### permissions.md (shipped)
Normally open: `fallback: allow`. Layer 1 denies `secret(*)` and `secret-write(*)`, so a secret is used only where a layer grants it. Locked denies in every mode (the fixed limits F1 to F3 of `rechte.md`): read, write, edit of `{secrets}/**/*.env` and `bash(*{secrets}/*.env*)`; read, write, edit of `{system}/**` and `bash(*{claude}*)`. `grant_files` lists the files that hold grants: `{permissions}`, `{entry}`, `{config}`, `{modes}/**`, `{rights}`, `agentMaster.md` and `tools.md` of agents and workflows, `tools.md` of projects, `{providers}/*.md`, the hook scripts (`{tools}/vault/**`, `watch`, `ntfy`, `telegram`), `{triggers}/**` and the run files a chat is resumed from (`events.jsonl`, `meta.json`, `session.md`, not `log.md`). It is number 13 of the catalog (`@grant_files`); `write({modes}/**)` and `write({rights})` count as part of it even where a tree's list lacks them (`modes.ALWAYS_GRANT`, and in the `modes:` path `rules._MODE_GRANTS` as a locked ask). The file has no `modes:` block any more: the modes are the mode files. Reasons per line are in the body of the file, not in comments. `money_limit`, `audit`, `service_token`, `sandbox` stay here.

### rechte.md and modes/ (shipped)
`rechte.md` (`paths.rights`, default `files.RIGHTS`) is the catalog: Markdown tables under `## <group>` headings, rows `| Nr | Recht | Regeln | Grundsatz | Fragen | Teil von |`. `Regeln` are rule texts in backticks (`@grant_files` = the list of permissions.md). `Grundsatz`: `offen` (base allows), `zu` (base denies: 31, 32), `frage` (the core asks by itself: 22, `shell-unparsed`). `Fragen`: `ja`, `fest` (the ask is locked), `nein` (may not be under `fragt`). `Teil von`: the number lies inside another one (13 in 12, 14 in 13, 71 to 74 in 41). Rows with an id `F<n>` are the fixed limits: no mode can name them; their rules must be denied in permissions.md (`lm check` warns), the others are in code (`unsafe_check`, the two exceptions of `decide`). Numbers 63, 64 (`browser-key(...)`) have no effect yet: no check of that kind exists.

`modes/<mode>.md` (`paths.modes`, default `files.MODES`; `_*` and README are no modes; sorted by `order`, no `order` = not in the Shift+Tab cycle). Strict YAML frontmatter, every key known: `label`, `color`, `order`, `regel` (`darf-nur` | `darf-alles-ausser`, also written `Darf nur:` or `darf alles außer`), `rechte` and `fragt` (numbers, `"13 Name"` or ranges `"51-55"`; a number in one list only), `geheimnisse` (`service` or `service/account`), `fragt-nie` (`ja`: the mode never asks; bypass always), `extra` (`allow`/`ask`/`deny`/`locked` in rule syntax). The body is the mode text for the AI. Per number the state is `erlaubt`, `fragt` or `gesperrt` (`ModeSpec.state`): named under `fragt` asks; named under `rechte` is allowed (darf-nur) or blocked (darf-alles-ausser); not named is blocked under darf-nur, and under darf-alles-ausser takes the state of the number it lies inside (a number that cannot ask is allowed then). `modes.compile_rules` makes the mode layer: blocked = locked deny on every rule of the number; fragt = ask, locked when `Fragen: fest` (in a never-asking mode a `zu` number under `fragt` gives no rule: it stays closed); erlaubt = nothing, except a `frage` number named under darf-nur (an allow). The rules of a number skip the numbers inside it whose state differs (`Rule.exclude`). `geheimnisse` adds `allow secret(...)` (an error when 31 is blocked, or when 31 is under `fragt`). Errors (bad YAML, unknown key or number, both lists, a bad rule) make only that mode unusable (`preset["error"]`, `build_layers` raises with the reason); a broken or missing catalog makes every mode unusable. `modes.presets(home)` is cached on the Home by size and time of the mode files, the catalog and permissions.md; it returns None (= read the `modes:` block of permissions.md, older trees) only when there is neither a mode file nor a catalog, so deleting the mode files of a switched tree is an error, not a way back. `modes.findings(home)` feeds `lm check`. `update_tree` does not add the shipped `modes/` and `rechte.md` to a tree that keeps its modes in permissions.md (note in `.notes`).

**Bypass never asks.** `rules.decide` turns every `ask` into `allow` when a layer has `no_ask` (the mode named `bypass`, or a mode file with `fragt-nie: ja`; `rules.is_bypass`, `rules.mode_never_asks(home, mode)`): rules, the fallback, `shell-unparsed`, categories, `new-tool`. A sub-agent uses the layers of its chat, so it is covered too, and the `ask` tool answers "asks nothing" there. Denies stay (locked denies, `secret(*)`, `unsafe` arguments, `money_limit`). Fixed exceptions: a locked ask on write/edit (a grant file under `fragt`) becomes a deny there, and an unreadable shell line that names secrets, `.env` or claude is denied (in modes that ask it is asked even where a rule allows unreadable lines). The shipped bypass blocks 13 (with 14); a tree may block only 14. A tool run unasked in such a mode is not hash-approved for other modes.

### init.py
- `init_tree(target=None, vault_repo=None, *, git="git") -> InitResult(root, created, vault, warnings)`: target default `Home.resolve_root` (`$LIGHTMIND_HOME`, else `~/lightmind`). Refuses a target that already holds `lightmind.md` (FileExistsError), never overwrites a file, renames `dot-x` template files to `.x`, makes files that start with `#!` executable, and records the created paths in `<state>/templates.json` (`{"version", "shipped": [...]}`). With `vault_repo` (URL or path; a value that starts with `-` or holds a control character raises ValueError before anything is created) the repo is cloned with `git -c protocol.ext.allow=never clone --quiet -- <repo> <dest>` and `GIT_ALLOW_PROTOCOL=https:ssh:git:file` (no ext::, no plain http) into `<paths.vault>/<repo-name>/`, `paths.vault` in the new `lightmind.md` points there (comments and layout kept), the clone is added to the tree's `.gitignore`, `vault/README.md` stays beside the clone and nothing is written into it. A failed clone leaves the default vault and reports the reason in `warnings`.

## tools.py
Uses `Tool, ToolResult, Check, Decision, RuleContext, SessionState, Agent`. Imports `files, rules, secrets, runs, model`.

## loop.py
Uses `Event, Message, Tokens, Request`. Imports `context, tools, runs, hooks, providers.base, model` (late: `rules`, `secrets`). The hook runner (`_run_hooks`, `_shell`, `_vars`, `_subst`, `_hook_text`, `HookOutput`, `HOOK_TIMEOUT`, `HOOK_CONTEXT_MAX`) lives in `hooks.py` and `list_sessions` / `SessionSummary` in `runs.py`; `loop` re-exports them all. Two parts: the tool loop here, the chat sessions in "Session API" below (same module).
- `stream_loop(provider, ctx, dispatcher, run, messages, *, model, effort, context_limit, handover_at, switch_at, max_turns=50, budget_tokens=None, budget_usd=None, on_event=None, result=None, handover_when_done=False) -> AsyncIterator[SessionEvent]` and `run_loop(...) -> LoopResult(status, final_text, tokens, messages, exit_reason, switch_to, context_tokens)` (the same without streaming). `messages` already ends with the new user message and grows in place; the outcome is written to `result`. Every event goes to `run.event(<lowercase class name>)` and `on_event`; every Message goes to a `message` event (that is what resume rebuilds); usage goes to `run.add_usage` after each turn (cost from `prices.md`).
- Providers with `owns_loop = True` (claude_sdk) run ONE turn per iteration; their ToolCall events are informational and are not executed again. For API providers the loop executes each ToolCall through `dispatcher.call` (in order), appends `Message("tool")` and yields `ToolDone`.
- Decisions between turns (a model call is never interrupted); a tool call of a finished turn is always answered first, so the message list stays consistent:

| after a turn | `LoopResult` |
|---|---|
| `Error` rate_limit / billing_error | `paused`, exit_reason = kind, `switch_to` = next account of `fallback[run.account]` ("" for agents with a fixed `provider`, or no chain) |
| `Error` max_turns | `paused`, exit_reason `max_turns` |
| any other `Error` | `failed`, exit_reason `<kind>: <message>` |
| `RateLimit` >= `switch_at` | `switch_to` set (if a chain exists); `paused` only while work remains; without a chain one `Notice("limit")` per loop |
| `budget_tokens` reached while work remains | `budget` (counts input + output + cache_write; cache reads are free) |
| context >= `handover_at` x `context_limit` while work remains (or always with `handover_when_done`, which chats set) | `handover_instruction()` is appended ONCE, the next turn writes the handover, then `handover` |
| a turn without tool calls | `done` |
| `max_turns` used up | `paused`, exit_reason `max_turns` |

  Context size = `provider.context_tokens` (prompt size of the last model call; claude_sdk) else the turn's `input + cache_read + cache_write`.
- **Cancellation:** if the tool loop is cancelled or closed (`CancelledError`, `aclose`), every call of the turn without a result gets `Message("tool", "cancelled by user", tool_call_id=...)` (appended and logged) before the exception goes on, so the history never holds a `tool_use` without a result (the API answers 400 forever otherwise). `resume_session` does the same for a trailing assistant message whose calls lack results (and logs it).
- Provider exceptions (`ProviderError`, e.g. `NotLoggedIn`) are logged as an `error` event and re-raised: `run_loop` raises, it does not return `failed` for them.

## providers/base.py
`Provider` protocol (`caps: Caps`, `turn(req) -> AsyncIterator[Event]`, `async usage() -> AccountUsage`). Optional attributes the loop reads with getattr: `owns_loop` (bool, default False), `context_tokens` (int).
- `resolve_account(home, requested, agent_provider, project_provider) -> str`: first set value wins (chat switch, agent, project, `providers` default); aliases are followed (cycle safe); a set but unknown name is an error, never skipped. Every value may be a list of accounts (`provider: [claude-abo, claude-abo-2]` in an agent, a project or `defaults`; `--account a,b`): the first one that is free right now wins (`accountpick.first_free`), the first one when none is. One name is taken as it is.
- `resolve_model(home, account, requested) -> str`: `requested` (or `settings.defaults.model`); a tier name is looked up in `tiers` under the account name, its `type`, then its family (`claude-subscription` and `anthropic-api` share `claude`); any other name is a fixed model and passes through.
- `make_provider(home, account, dispatcher=None)`: lazy adapter import by account `type` (`ADAPTERS`); `NotImplementedError("... comes with phase 2")` for types without an adapter.
- Helpers `resolve_alias(cfg, name)`, `settings(home)`, `settings_defaults(home)` (`{}` when the tree has no settings).
- Extra types (additive): `ProviderError(message, kind)` for "cannot even start a turn" (in-turn failures stay `Error` events); `ToolDone(id, name, ok, text)` mirrors a tool result for UIs; `Notice(kind, text)` (handover | switch | limit | warning | hook); `SessionEvent = Event | ToolDone | Notice`.

## providers/claude_sdk.py
`ClaudeSdkProvider(home, account, dispatcher=None)` implements `Provider` with `owns_loop = True`; `claude-agent-sdk` pinned in `pyproject.toml`, options per `spikes/sdk/RESULT.md`.
- **One turn = one short-lived CLI process.** The module function `_query(prompt=, options=)` (the seam tests replace) wraps `ClaudeSDKClient`: `connect(prompt)` starts the CLI and sends the message, `receive_response()` yields up to and including the result, `disconnect()` runs in a `finally`. Nothing is resident between turns (measured: no child process after a turn). The conversation continues with `resume=<sdk session id>` (`provider.session_id`, persisted by the session). A resume the CLI does not know falls back, once, to a fresh conversation with a replay of the logged history (`Notice("warning")`).
- **Closing the turn's iterator ends the CLI before `aclose()` returns**, whether the consumer stops early (Esc), our code raises (`NotLoggedIn`) or `connect` fails. It takes about 2 to 3 s (measured 2.2 s: stdin EOF, the CLI flushes its session file, at most 5 s grace, then terminate), so a UI that must stay responsive runs `aclose()` as a task. This is why `_query` does not use `claude_agent_sdk.query()` (SDK 0.2.168, found by the live test): that generator does not close the generator it wraps (PEP 533), so after an early stop or an exception the CLI lived on until the garbage collector finalised the inner generator on the event loop, and for good (still running 20 s later) when the loop closed first.
- Options: `system_prompt={"type":"file"}` (the cache-stable prefix plus a one-sentence note on system reminders, written content-addressed into the `state` folder, which the rules lock against agents), `setting_sources=[]`, `tools=[]`, `skills=[]`, `strict_mcp_config=True`, ONE in-process MCP server `lm` exposing `dispatcher.schemas()` (handler = `dispatcher.call`, errors become `is_error` results), `allowed_tools=["mcp__lm__<tool>", ...]`, `model` / `effort` from the request (`low` also sets `thinking: disabled`), `max_turns`, `cwd` = tree root (`provider.workdir` overrides), env switches `CLAUDE_CODE_DISABLE_CLAUDE_MDS / AUTO_MEMORY / ATTACHMENTS / BUNDLED_SKILLS`, and blank `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` (a subscription account never falls through to a pay-per-token key).
- **Guard:** a `PreToolUse` hook denies anything that is not `mcp__lm__*` and anything `rules.decide_all(checks_for_call(...))` denies (fails closed on errors); asks are left to the dispatcher. Denials are logged as `guard` events, passes are kept in `provider.guard_log`.
- **Login lives in the tree (portable).** The account's `config_dir` (key in `providers/<account>.md`, template `system/claude/claude-abo`, relative to the tree root; absolute paths are kept) becomes `CLAUDE_CONFIG_DIR`; a `CLAUDE_CODE_OAUTH_TOKEN` in the account's `secret` file is passed too and wins over the stored login; without a token file the environment's `CLAUDE_CODE_OAUTH_TOKEN` is blanked so it cannot override the account. No `config_dir` and no token = the system default login: dev/test only, one `logging` warning and `provider.warnings` (the session shows it as `Notice("warning")`). `Account.config_dir` is read directly.
- **`login(home, account) -> int`**: the one-time interactive login. Runs the bundled CLI as `claude auth login --claudeai` attached to the terminal with `CLAUDE_CONFIG_DIR` set (folder created), so the user signs in once in the browser and the credentials end up inside the tree. `lm login <account>` calls it. Never run by agents or tests. An account without `config_dir` raises `ProviderError` saying what to add.
- **`NotLoggedIn(ProviderError)`**, kind `auth`, message exactly ``not logged in: run `lm login <account>` ``: raised by `turn()` when the CLI reports no login (also for an expired or invalid token). Everything else that goes wrong inside a turn is an `Error` event: `rate_limit`, `billing_error`, `overloaded`, `max_turns`, `other` (a CLI crash carries the masked tail of stderr). A missing CLI raises `ProviderError`.
- Events: assistant text -> `Text`; tool use -> `ToolCall` (name without the `mcp__lm__` prefix); tool result -> `ToolDone`; `RateLimitEvent` -> `RateLimit` for `five_hour` and `seven_day` (from `raw["unifiedWindows"]`); `ResultMessage` -> `Usage` (per invocation, not cumulative; `provider.cost_usd` keeps the CLI's own `total_cost_usd`, an estimate for subscriptions). `provider.context_tokens` = prompt size of the last model call.
- `usage()` returns the last seen 5 h / 7 d utilization (`est=True`, kept in `<state>/limits-<account>.json` so it survives the process).
- Request mapping: only the newest user message is sent on a resumed conversation; `Request.state` goes in front of it on a fresh conversation or when it changed; a fresh conversation with history gets that history replayed as text (account switch, handover aside).

## providers/anthropic_api.py and openai_compat.py
HTTP adapters over httpx (no SDK), one model call per `turn()`, `owns_loop = False`: `loop.py` runs the ToolCalls and calls `turn()` again. Shared helpers in `providers/_api_common.py` (key lookup, error classes, SSE reader).
- Registered in `ADAPTERS`: `anthropic-api` -> `AnthropicApiProvider`; `openrouter`, `openai`, `openai-compatible`, `openai-compat` -> `OpenAICompatProvider`. Constructor `(home, account, dispatcher=None)`; `provider.transport` may be set to an `httpx.MockTransport` (tests).
- Key: `secrets.provider_env(home, account.secret)` per turn (`ANTHROPIC_API_KEY`; `OPENROUTER_API_KEY` / `OPENAI_API_KEY` / `API_KEY`, or the only variable of the file). A missing secret raises `ProviderError(kind="auth")` naming the secret to create. A local `openai-compatible` account without `secret:` sends no Authorization header. The key is masked out of every error text and never enters events or the run log.
- Optional keys of the provider file (read from its frontmatter): `base_url`, `max_tokens` (default 32000 for Anthropic), `referer` / `title` (OpenRouter headers).
- Anthropic: `POST {base_url}/v1/messages`, stream. System = [prefix block with `cache_control: ephemeral`, state block]; tools = `Request.tools` unchanged; assistant tool calls = `tool_use`, consecutive `tool` messages = one user message of `tool_result`. Effort -> `output_config.effort` for fable/mythos/opus/sonnet/haiku 5.x and opus 4.6-4.8 / sonnet 4.6; never `thinking`; older models get no effort. Events: RateLimit (highest utilization of the `anthropic-ratelimit-*` headers, first), Text per delta, ToolCall at block end, Usage (input = uncached, cache_read, cache_write) last.
- OpenAI-compatible: `POST {base_url}/chat/completions`, stream with `include_usage`; tools as function calling; Usage input = prompt - cached - cache_write. OpenRouter only: prefix `cache_control`, `reasoning.effort` (xhigh and max -> high), RateLimit from `x-ratelimit-*` headers if present.
- Errors (events; the turn ends without Usage): 429 -> `rate_limit`, 529/503/`overloaded` -> `overloaded`, 402 / "credit balance" -> `billing_error`, 401/403 -> `auth`, the rest and network failures -> `other`. The loop turns `rate_limit` and `billing_error` into `paused` plus the fallback account.
- Cost: prices come from `models:` of the account file (full API model names; see the `_example-*` files).

## Session API
In `loop.py`, used by the CLI (`lm chat`, `lm run`) and the Orbit TUI. A session is one chat: settings, conversation, dispatcher, provider, and a run folder that holds everything needed to resume it. No function here calls a model except `Session.send`.

Settings read from `home.settings` (the frontmatter of `lightmind.md`; `{}` when absent): `defaults{server, provider, model, effort, context, mode, max_turns?}`, `context.handover_at`, `shell` (also used by the dispatcher), `on_start`, `on_prompt`, `on_end`.

```python
open_session(home, server=None, agent=None, project=None, account=None, model=None, effort=None,
             context=None, mode=None, tools_on=None, tools_off=None, secrets=None,
             rules=None, asker=None, hook_gate=None) -> Session
resume_session(home, id, asker=None, hook_gate=None) -> Session      # id or unique prefix
list_sessions(home, limit=20) -> list[SessionSummary]                # newest first
run_on_start(home, session) -> list[str]                             # SessionStart hooks
run_on_prompt(home, session, prompt) -> HookOutput                   # UserPromptSubmit hooks (Session.send calls it)
run_on_end(home, session) -> list[str]                               # SessionEnd hooks (Session.close calls it)
```
- `open_session`: first hit wins per setting: argument, then agent file, then (account only) project `provider:`, then `settings.defaults`. **The project:** `project=` (`-p`) wins; else the agent's `project:` is used (a name that is not a valid, existing project is a `ValueError` naming the agent, before a run folder exists); it loads exactly as `-p` does (its memory and assets, `$PROJECT`) and grants nothing (a project's tools.md is not merged into any rule). A resumed chat keeps what its record says. `server=None` is `defaults.server`; any other server raises `NotImplementedError("remote servers come in the next step")`. `context` is a size (`"200k"`, `1_000_000`). `tools_on` / `tools_off` are tool, skill or `name/account` connector names (`SessionState.tools_added / tools_removed`). `secrets=["name/account"]` become layer-4 rules `allow secret(<ref>)`; `rules=[Rule, ...]` are ready-made layer-4 rules (the CLI's `--allow` / `--deny`, origin `session:cli`): an origin that does not start with `session:` is dropped at resume. `tools_on` / `tools_off` accept every name `list_skills()` / `list_tools()` know, a tool with a README only included. Bad input (unknown agent, mode, project, account, tool) fails before a run folder exists. No model call and no CLI process is started. The loop never passes `api` to the Dispatcher.
- `Session`: `id` (= run id), `info -> SessionInfo(id, server, model, account, mode, effort, agent, project, ctx_used, ctx_limit, cost_usd, cost_est, status, limits{five_hour, seven_day}, ctx_pct)` for the status line, `async send(text) -> AsyncIterator[SessionEvent]`, `set(model=, mode=, account=, effort=, tools_on=, tools_off=)`, `close(status="done", reason="closed") -> list[str]` (runs on_end, finishes the run, returns the lines to show), plus `asker` (settable), `hook_gate`, `messages`, `start_context`, `last_result`, `run`, `dispatcher`, `provider`.
- `send`: runs the on_prompt hooks (in a thread), then the turn through `stream_loop` with the between-turn rules above (`handover_when_done=True`). Yields the provider's `Text / ToolCall / ToolDone / Usage / RateLimit / Error` events plus `Notice`s. One turn at a time (`RuntimeError` otherwise); an empty message is a `ValueError`; a closed session raises. Provider exceptions (`NotLoggedIn`) propagate and leave the session usable. Stopping the iteration early (`aclose()`) shuts the CLI process down before it returns (2 to 3 s, see claude_sdk); the session is then free for the next message.
- `set`: validated now (unknown mode / account / tool raises, an account without an adapter raises `NotImplementedError`), recorded now (`info` follows at once), applied at the START of the next turn (dispatcher rebuilt for tool changes, keeping the tool-out counter and masker; provider swapped for an account change; the prefix rebuilt for a mode change). A tier is resolved again for the new account. A new account has no memory of the conversation: the logged history is replayed once.
- **Automatic follow-ups after a turn:** a limit warning or hard limit error with a fallback chain switches the account for the next turn (`Notice("switch")`; the unanswered message is not retried). A full context (see the table above) ends in a handover: the model writes `## Handover` into `log.md` of the run folder (or its last answer is used), the conversation restarts fresh (`reset` event, SDK conversation dropped) and the next user message carries `handover_task(...)`; this survives close and resume.
- **Persistence (run folder, all through runs.py):** `meta.json` follows account / model / mode; `session.md` is the layer-4 state (for people); `events.jsonl` starts with a `session` event (a run is a chat session iff its first event is one) and gets a new one after every turn and every `set`: `sdk_session_id, server, agent, project, account, model, model_req (tier or name as requested), effort, context, mode, ctx_used, handover`. Every Message is a `message` event, a handover restart a `reset` event. **The run folder is writable by agents, so resume trusts only the conversation in it.** The same facts plus `state{mode, account, model, tools_added, tools_removed, data_added, rules}` are written to the trusted record `<state>/sessions/<run id>.json` (`RunDir.write_trusted`, `runs.read_trusted`, `runs.trusted_file`; the state folder is locked for agents). `resume_session` takes the messages from `events.jsonl` and everything else from that record, checks it again (agent and project must still be listed, the mode still defined, the account still known; ValueError otherwise), drops session rules whose origin does not start with `session:`, names the run by its folder (not by a field of `meta.json`), sets the run `running` again, continues the SDK conversation (`resume=`) and keeps the tool-out numbering. A chat without the record cannot be resumed (ValueError). `list_sessions` rows (`SessionSummary`): `id, title (first words of the first user message), agent, project, server, account, model, mode, status, start, last_active, cost_usd, cost_est`.
- **One writer per chat (the session lock).** `open_session` and `resume_session` take `<state>/sessions/<run id>.lock` (`runs.acquire_lock`: one line `<pid> <process start>`); `Session.close` and `Session.hand_over` give it back (`runs.release_lock` removes only a lock of this process). `resume_session` returns a normal session when the lock was free, was left by a process that is gone, belongs to a pid that another program has now (the start time differs: pid reuse) or is this process's own; it writes the run's `pid` anew (so `run_result` does not call a live resumed chat `process died`). **When another live process has the chat open the result is read only:** `Session.readonly` / `readonly_by` (that pid), no provider (`provider` is None), nothing written (no `session` event, no meta, no lock, no cancelled results for a trailing tool call, no hooks); `send` and `set` raise `loop.ReadOnlyChat`, `close` and `hand_over` only mark it closed. A session that cannot be built gives its lock back. `Session.hand_over()` gives a chat to another process (a new tab resumes it by id): it writes the record, sets the run `paused` without an end marker (`RunDir.park`), releases the lock, runs no on_end hook, and closes the object. The locks sit in the state folder, which the rules lock for agents in every mode (tested), so an agent can neither forge nor free one.
- **Hooks (`on_start`, `on_prompt`, `on_end`) are Claude Code hook compatible.** Entry: `{run: <command>, show: bool, context: bool, timeout: seconds (default 15), max: chars of context kept (default 8000), env: {NAME: value}}` or a plain command string. The command runs in the tree root, in the configured `shell` (Git Bash on Windows, like Claude Code hooks), starts from `home.runtime_env()`, and gets Claude Code's JSON on stdin: `hook_event_name` (`SessionStart` | `UserPromptSubmit` | `SessionEnd`), `session_id` (the run id), `cwd`, `transcript_path` (the run's `log.md`, else `events.jsonl`), `prompt` (on_prompt), `source` (`startup` | `resume`, on_start), `reason` (on_end). Environment: `LM_HOME`, `LM_RUN`, `CLAUDE_PROJECT_DIR` (= the tree root), UTF-8 for Python, plus the entry's `env`. `{key}` placeholders (any `paths:` key, `root`, `run`) are replaced in `run` (paths as written) and in `env` values (absolute paths); shell braces such as `{print x}` stay. The log (`on_start` / `on_prompt` / `on_end` events) holds the parsed, masked text, never the raw stdout. Output: plain stdout is the text; a JSON object is read like Claude Code does (`hookSpecificOutput.additionalContext` is the text, `systemMessage` is always shown); other JSON-looking output (`42`, an object without those keys) is plain text or nothing. `show` displays the text, `context` keeps it: for on_start in `session.start_context` (the volatile `State` block, never the cached prefix), for on_prompt appended to THAT user message as a `<context source="on_prompt">` block (never the system prompt; the logged message is what the model saw). A nonzero exit, a timeout or a missing shell is a `warning: ...` line (shown whatever `show` says), never an exception; the message is still sent. On timeout the whole process tree is killed.
- **Hooks are trusted configuration** of the tree owner: `lightmind.md` changes only after the user confirms, so they run without the per-call rule check. Two safeguards remain: every output passes a `Masker` that knows ALL secret values of the `secrets` folder (not only those injected into a tool so far) and the credential-like variables of the process environment (names containing TOKEN, SECRET, PASSW, API_KEY, CREDENTIAL, PRIVATE_KEY; a hook inherits the environment), so a secret cannot reach the model, the logs or the screen through a hook. The output is parsed first (JSON writes a value differently from its plain form), then masked, and only then cut to `max`; command lines, veto reasons and warnings are masked too; and an optional `hook_gate(event, command) -> reason | None` can veto a command (a reason, or an exception in the gate, skips it and is reported as a warning; fail closed). Keep `lightmind.md` unwritable for agents (the template's locked rule) or hooks become a way around the rules.
- Known limits: `send` yields the assistant message when it is complete (no token streaming yet); a context size above 200k (`Request.context`) makes `claude_sdk` send the model as `<model>[1m]`; `anthropic_api` and `openai_compat` do not ask for a bigger window yet (the size is then only Lightmind's handover limit, the API stays at its 200k); the SDK's own compaction is untouched (it triggers late, far above `handover_at`).

## runs.py
Uses `Run, Task, Tokens, SessionState, Event`. Imports `files, model`.
- `new_run_id(agent, now)`, `RunDir(home, run, task)` with `.run`, `.path`, `event()`, `write_session()`, `tool_out()`, `add_usage()`, `finish(status, exit_reason)`; `load_prices(home)` (= `home.prices()`: the model prices of `providers/*.md`), `compute_cost(prices, model, tokens) -> (usd, est)`, `list_runs`, `show_run`, `cost_summary`; `list_sessions(home, limit=20) -> list[SessionSummary]` and the `SessionSummary` row (chat sessions among the runs; re-exported by `loop`), `RunDir.write_trusted(data)`, `trusted_file(home, run_id)` (`<state>/sessions/<id>.json`), `read_trusted(home, run_id) -> dict | None`: the part of a chat session that resume trusts (see Session API).

- **Session lock (`runs.py`).** `lock_file(home, id)`, `acquire_lock(home, id) -> int` (0 = this process has the chat now, else the pid of the live process that has it; the check and the write are one step under `<state>/sessions/.lock`), `release_lock`, `lock_holder(home, id) -> int` (0 when nobody live), `process_stamp(pid) -> str` (start time: `GetProcessTimes` on Windows, `/proc/<pid>/stat` field 22 on Linux; '' when it cannot be told, then a live pid counts as the holder), `find_runs(home, prefix) -> [Path]` (the folders whose id starts with the prefix; an empty prefix matches none), `RunDir(home, run, task=None, write=True)` (`write=False` touches nothing: a chat that is only read), `RunDir.park(exit_reason='')` (status `paused`, no end marker). Tests: `tests/test_session_lock.py` (a real second process holds the lock, an orphan is taken over, pid reuse, nothing written read only, hand-over).
- **Runs that start runs (phase 2).** `Run` also holds `parent` (run id, from `LM_PARENT`), `depth` (from `LM_DEPTH`) and `pid`; `open_session(..., run_id=, max_turns=, max_usd=)` sets them (`pid` = this process). The tool environment of every run (`Dispatcher._env`, hooks) carries `LM_DEPTH = depth + 1` and `LM_PARENT = <run id>`, so a run started from a tool is one deeper; the variables are a guard against runaway chains, not a security boundary (an agent can overwrite them in its own command; `max_parallel` and `--max-usd` still bound the damage). `RunDir.write_result(dict)` writes `result.json` (`run_id, status, exit_reason, text, cost_usd, cost_est[, result]`) before `finish`. `run_result(home, id)` reads it with the meta (a run whose `pid` is dead without an end is marked `failed`, exit_reason `process died`; a detached run without a process after `STARTUP_GRACE` s `never started`); `wait_runs(home, ids, timeout)` polls; `resolve_run`, `pid_alive`, `duration('30m')`. Parallel slots: `claim_slot(home, run_id, limit) -> bool` / `release_slot` keep one file `<state>/slots/<run id>.slot` (pid) per running `lm run`, counted under an O_EXCL lock file; slots of dead pids are freed on the next claim.
- **Limits.** `stream_loop(..., budget_usd=)`: after a turn with work remaining, `run.cost_usd >= budget_usd` ends `budget` (exit_reason `$X`). Backends that own the loop get `Request.max_usd` (remaining budget; claude_sdk passes `max_budget_usd`, its `error_max_budget_usd` becomes `Error("budget")` and status `budget`). `Session.max_turns` / `Session.max_usd`; the agent's `budget.usd` also applies (the stricter wins).
- `schema.py` (stdlib): `validate(value, schema) -> [errors]` (type incl. lists, required, properties, items, enum, additionalProperties false; the rest of a schema is ignored), `extract_json(text)`, `check_answer(text, schema) -> (value, errors)`.

## accountpick.py
Which account a run starts on when more than one is allowed (the logic of the interim tool `tools/account-picker`, now in the core). `names_of(value)` / `as_text(value)` read and write a `provider` value (name, `a, b`, `[a, b]` or a list; files store the text `a, b`). `free(home, name, limit=None) -> (bool, reason)`: usable (logged in / key present) and, for a subscription, neither the 5-hour nor the 7-day window at or over `limit` (default `providers.switch_at`, 90 %); a window whose reset time has passed does not count. `first_free(home, names)`: the first free one, else the first. `start_account(home, name, chain)`: a NEW chat leaves `name` for the first usable account of `chain` (its fallbacks) when `name`'s 7-day window is at or over 95 % (`WEEK_START_LIMIT`); `open_session` does that only when no account was asked for by name and no agent pins one. Imports `accounts` late. Tests: `tests/test_kontowechsel.py`.
- **Account switch at a limit (AN-760).** `Session.set(account=)` builds the new provider with an empty conversation id, so the next turn starts fresh on the new account with the logged history in its first request. The trusted record keeps `sdk_session_id` together with `sdk_account` (the account that made it); right after a switch both name the new account and the id is empty. `resume_session` uses the id only when `sdk_account` equals the chat's account (`loop._own_sdk_session`); a record without the field is trusted. `claude_sdk` also treats "No conversation found" that arrives as a `ResultError` or in the stderr of a failed CLI as a lost conversation (one replay). An agent whose `provider` is a list moves on within that list at a limit (`loop._fallback`); a single fixed account still pauses.

## accounts.py
`account_status(home, name)` / `list_accounts(home)` (default account first) give plain JSON-safe dicts: `name, type, default_model, use, fallback, state, hint, five_hour, seven_day, resets_at, limits_seen` plus `config_dir, logged_in` (subscription) or `secret, key_present` (API). `state`: `ready | login-missing | key-missing | no-key-needed | no-adapter | config-error`. `hint` is the one next-step line shared by CLI and TUI: `not logged in: lm login <account>` / `key missing: lm secret set <secret>` (or ''). A subscription counts as logged in when `<config_dir>/.credentials.json` EXISTS (or its token secret exists): the file is never opened. Limits come from `{state}/limits-<account>.json` as the chats left them. `default_var(ref)`: `ANTHROPIC_API_KEY` for `anthropic/*`, `OPENROUTER_API_KEY` for `openrouter/*`. ## Security model
The rule checker is a guard against mistakes, not an operating-system sandbox. Permissions are open by default (fallback `allow`); what stays shut by default are secret values.

What it guarantees:
- **File tools.** `read` / `write` / `edit` paths (and tool parameters of kind `read-path` / `write-path`) are compared in canonical form: links resolved, `..` and trailing dots / spaces removed, case folded on Windows. Windows aliases (`:stream`, 8.3 names, UNC prefixes) are denied. The built-in tools and path parameters open exactly the place that was checked; a path that resolves elsewhere is refused.
- **Secrets.** `.env` values are injected only into tools whose rules allow that secret, masked in all tool output, and never typed by the model: the `secrets` tool returns placeholders. Provider credentials and the service token are reserved: no tool receives them and the `secrets` tool refuses them, in every spelling (refs compare case-folded on Windows; names with trailing dots / spaces or path separators do not parse).
- **Money.** The ledger fails closed on NaN, Infinity or unreadable books.
- **Tool values.** A tool's `match` value is split into separate values (lists, whitespace, `,` `;` `<` `>` and quotes) and each is checked; with `tools.as_functions` on, the tool is handed that same list.
- **Shell lines** run in the shell of the `shell` setting (default `bash`; Git Bash on Windows; a missing shell is an error, never a fallback to cmd.exe) and are read in POSIX grammar: one check per simple command, an allow rule must cover all of them, a deny / ask rule fires on any. A line that does not parse cleanly (unbalanced quote, open `$(`, trailing backslash, `#` after an escape, an unquoted `#` inside `$(...)` or backticks, blanks other than space / tab) asks. **The shell itself is not taken from an agent-writable place:** `resolve_shell` ignores PATH entries that are relative, equal the current directory or lie anywhere inside the tree root, so a `bash` an agent drops into the tree (even in a folder on PATH) never becomes the shell. **PATH order:** the tree's `bin` is appended at the END of PATH for every process the core or a launcher starts (`runtime_env`, the launchers), so a file planted there cannot shadow git, bash or python in a process that carries secrets. **Resume** trusts only the conversation of a run folder (see Session API), and the terminal never receives control characters from model or tool text (see cli.py).

What it does not guarantee: an agent with unrestricted `bash` can bypass command-pattern rules (`eval`, `bash -c`, scripts it writes first, interpreters, `xargs`, aliases are not looked into). Containing that needs an OS sandbox (`sandbox:` is reserved in the permissions file for a later one) or not granting `bash(*)`.

Known limitations: further parser-differential findings on bash patterns (the checker reading a line differently from bash) are accepted, unless they let a secret default be bypassed through a non-bash tool (`read` / `write` / `edit`, tool parameters, the `secrets` tool, secret injection).

- **Frames of the start screen (`MapScreen`, `profile.py`; plan addition C, measured with `LM_PROFILE=1`).** The landing used to cost 77 to 85 % of a core while nobody touched it, so frames came at 10 to 13 a second instead of 20, unevenly (95th percentile of the interval 170 to 195 ms, worst 300 ms) and everything else on the UI thread waited. Measured causes: (1) Textual turning the Rich Text of the map and the wordmark into strips (Rich Text, Content, Strip: about 45 microseconds per styled run, 36 ms of the 42 ms of the map frame and 10 ms of the wordmark, every frame); (2) `tui.chat` and `loop` imported in a thread while the animation ran (the import thread took 12 to 22 % of a core in the intro, 5.7 s once on a cold disk); (3) full garbage collections of 45 to 90 ms every 2.4 s (Textual leaves a reference cycle behind every strip it draws: `Strip.divide` caches the one-element list that holds the strip, so about 1500 objects a frame are freed only by the collector, and a full collection also walks every object of Textual, Rich and this program); (4) `data.menu` / `data.layout` read from the files in every tick (`home.settings` is several stats), and the menu line redrawn every tick. ## launch.py (where a chat opens; plan `plan/PLAN-CONFIG-TABS.md`)

## slash.py (slash words anywhere in a message; plan `plan/PLAN-SLASH.md`)
`slash.py` imports `context` late (the text of a skill) and nothing else; the Orbit chat (`tui/chat.py`) and `lm chat` (`cli.py`) read an input line with it, so both treat it the same way. A slash word starts with `/` at the start of the input or after whitespace and stands outside code (`` `...` `` and ``` blocks): `a/b`, `https://x` and `C:/x` are none. `parse(text, Catalog) -> Parsed(text, acts, skills, then, error, unknown)` runs nothing and reads no tree; the surface passes its own `Catalog(builtin, skills, rows, takes)` (`rows` = the `ui.slash` commands).
- **Skills** (`/arsenal`, also `/arsenal,`): stay in the text; every skill named is loaded for this turn, in order, each once (`message()`: one `skill_message` head per skill, then the text).
- **Commands that change a setting** (`COMMANDS`: `/mode /model /account /effort /ultracode`, and `/context` once a surface has it): run in order of appearance; the command and its one word (same line, no slash word) are cut out and the rest is sent when it is not empty (`/model opus /effort high explain X`). `takes` checks the word before anything runs: `/effort` against its list, `/model` against the account's models, tiers and what the tiers point at (an unlisted word counts only when no prose follows it, or when it looks like an id); `/mode` and `/account` are checked by the core when they run. A command that fails stops the rest and nothing is sent. Without a word a command runs as it always did (Orbit: its picker, `lm chat`: it prints the value).
- **Commands that end or leave the chat** (every other built-in and every `ui.slash` row: `/clear /exit /new /resume /settings /accounts /server /login /key /quit`): alone or last. With text before them the text is sent and the command runs after the answer (not after Esc or an error); with anything after them nothing is sent or run.
- **Commands that take the rest of the line** (`LINE`: `/tools`, `/skill`): only first, as before; elsewhere they are refused.
- **Commands that put text into the input** (`INSERT`: `/upload`, `/datei`; `Act.kind == "insert"`): anywhere, no word, nothing is sent. The surface cuts the word out (`take_out(text) -> (text, where it stood)`) and opens the native file dialog (`upload.py`: PowerShell `OpenFileDialog` on Windows, `osascript` on macOS, `zenity`/`kdialog` on Linux; none over ssh or without a display: the German notice `upload.NO_PICKER`, nothing changes; cancel changes nothing). The files are copied to `runs/<run>/uploads/` (a taken name gets `-1`, `-2`; over 500 MB the original path is used) and one line `[Anhang: <path>]` per file (relative to the tree root when inside it, forward slashes) is inserted at that place; the `read` tool description tells the model that such a line is a file the user attached. `lm chat` keeps the lines and puts them in front of the next message. Tests: `tests/test_upload.py`, `tests/test_tui_upload.py`; no test opens a dialog (`conftest.no_file_dialog`).
- `//word` is the plain text `/word`; other unknown words are text; only an input that is one unknown word (`/frobnicate`) is refused, with the old "unknown command" note.
- `Parsed.error` means nothing runs or is sent. Orbit shows it and keeps the line; `lm chat` prints it and puts the line back in the input where `readline` exists (`_prefill`; on Windows `input()` has taken it).
- Orbit: the popup opens for the slash word under the cursor anywhere in the text (`word_at`), is filtered by that word, Tab and Enter replace only it (`complete`); an open popup follows the cursor (the `selection` of the Input), Esc closes it until the next key. The line above the input shows `summary()` (`model opus · effort high · skills: arsenal · then clear`). `lm chat` prints the summary before it sends and completes with Tab where `readline` exists. Tests: `tests/test_slash.py`, `tests/test_tui_slash.py`.

## lm sync (`sync.py`; plan `plan/PLAN-SYNC.md`)
- **What it is.** The tree is the git working tree of a private repo (branch `main`); secrets travel as age files made with `pyrage` (a main dependency, no age binary). Imports `files` at the top, `secrets` and `tools` late. Everything is silent unless `sync.enabled(home)`: own `.git` in the tree root AND a machine name. The repo is NOT trusted (see Recipients).
- **Instance files (never synced, under `paths.state`):** `machine` (name; `$LM_MACHINE` wins; `Home.machine`), `local.md` (frontmatter laid over `lightmind.md` section by section in `Home._meta`, so `Home.settings` shows the result; e.g. `defaults.server`, `run.always_on: true`), `age.key` (private key, created with mode 600), `recipients-confirmed` (`<name> age1...` per line: the (name, key) pairs THIS instance confirmed), `sync-secrets.json` (`hashes`: plain-text hash of each secret as last agreed with the repo; `conflicts` with `why`; `recipients`: per secret the hash of the `.age` this instance wrote and the fingerprint of the recipient list it was made for; `removing`; `adopted`; `prev_fp`: per device the fingerprint, never the key, it had when last confirmed, for a warning only), `sync-status.json` (last result), `sync.lock` (holds the pid of its owner).
- **Repo content.** `.gitignore` gets a managed block (`# lm sync (managed)`, appended once): `system/`, `runs/*`, `secrets/**` with a positive list (`!secrets/**/`, `*.age`, `info.md`, `README.md`, `recipients`), `*.env`, `*.env.tmp`, `*.key`, `*.plain`, `*.lokal`, `*credentials.json*`. `.gitattributes`: `* text=auto eol=lf`, `*.age binary`. `secrets/recipients`: one line `<machine> age1...` per device. Secrets per file: `secrets/<name>/<account>.env.age` beside each `.env`.
- **Recipients: the repo's list is a proposal.** `read_list(home)` = (name -> key, problems) as the file stands; `read_recipients` = the same, or `{}` when there is a problem. A list is refused as a whole (warning in the checklist, `status` and every run, nothing is encrypted, add-device / remove-device / approve raise) when it holds a name twice, a key twice, a name outside `a-z 0-9 - _` (max 32), a line that is not `<name> <key>` (`#` comments and blank lines are fine), or a text that is no age key; nothing is renamed or guessed, text from the repo prints escaped. `effective_recipients` (= the list's lines that are a confirmed (name, key) pair, plus the own key) is what is ever encrypted for (`encrypt_ref`, `rewrap`, `reencrypt_all`). A key someone slips into the list, or a new key under a confirmed name, is therefore never used; `recipient_warnings` says `new device <name> ... not confirmed` or `key of <name> has changed ...` (checklist: short form without fingerprints). Confirmed by: `init`/`join` (the own key), `add-device` (the key it adds, the operator names it), `approve`, and `join` for the whole list when `confirm(list)` says yes (default: asks on a TTY, no TTY = no, a list with a problem is not even shown). `fingerprint(key)` = 32 hex digits of sha256 in groups of four. The confirmed list is pruned by PAIR (`_prune_confirmed`, after every pull and in remove-device): a pair stays only while the list has exactly that line, so a device that left or whose key changed loses its confirmation at once and an old key written back is not trusted again; `prev_fp` keeps only the old fingerprint for the "has changed" warning. A removal that comes with a pull is adopted at once. `_distrust_removed` (called by `_pull` after the fetch, before the rebase) looks at EVERY version of `secrets/recipients` among the commits that are pulled: a confirmed (name, key) that one version no longer has (the version before it had it) loses its confirmation even when a later version has the line again, because the final list alone would trust a device again that was off it in between; it then shows as `new device <name> ... not confirmed` (the old fingerprint, never the key, stays for the warning). `join` refuses (before the question, and again once its key exists; then everything is put back) when the repo's list holds ITS OWN machine name with another key (`recipients already lists <name> with a different key; refusing`): a line planted under a name that is easy to guess ('harness') would otherwise replace the own key at the user's yes. Without a terminal `join` confirms only the own pair.
- **`approve(home, name, fingerprint=None)` (`lm sync approve <name> [<fingerprint>]`).** Without a fingerprint it only shows the device and says how to confirm (compare with `lm sync status` on that device, then `lm sync approve <name> <fingerprint>`). With one (at least 16 of the 32 hex digits, dashes, colons and case ignored) it takes the sync lock, reads the list again, refuses unless the key under that name has that fingerprint (a pull may have changed it since it was shown), confirms the pair, makes every secret again for the new list and syncs, all under that one lock. `cli.py` needs the line (`choices`, `need`, the dispatch dict: `sync.approve(home, name, fingerprint)`), the second argument is optional.
- **Secret writes.** `secrets._write_env(..., home=)` (tool new/set/rotate, `lm secret set`, `/key` via `accounts.store_secret`) calls `sync.on_secret_written`: the `.age` is written at once, then `kick`: the COMMIT is made before it returns (so `lm secret set` ends with the `.age` in the history); pull and push follow in a registered thread. A sync of another process is waited for (`LOCK_WAIT` 20 s), a sync thread of this process is not (the caller may be the UI). Without a sync repo nothing happens.
- **`run(home, pull=True, push=True, lock_wait=0, held=False) -> Result(status ok|offline|auth|conflict|warn|skip, lines, warnings)`:** lock (waits `lock_wait` seconds; `held`: the caller has it); `_recover` (an unfinished rebase after a kill is aborted, its changed files saved under `state/rebase-saved/`; a detached HEAD stops the run); managed files; `reconcile(after_pull=False)`; `_commit` (message `sync <machine>: <n> Dateien`); fetch + `rebase origin/main` (an `.age` conflict is settled with the repo's file, or with its deletion; any other conflict, text or binary, ends with `rebase --abort`, tree as before, files named); `reconcile(after_pull=True)`; `_prune_confirmed` + `rewrap`; commit; push (one retry after a rejected push), then `rewrap` again and push again when the push had to pull. Offline: the commit stays, status `offline`, the next run catches up. **Before every push `_squash`:** when two unpushed commits touch the same `.age`, ALL unpushed commits become ONE commit with the same tree (clean index only), so a secret written for an older recipient list goes up only in its rewrapped form and never with the readable version of a removed device beside it. A rejected push pulls (with `_distrust_removed`), makes stale `.age` files again and commits them, squashes, and pushes once more. **Network:** fetch and push have `TRANSFER` (300 s), every other git call with a network `NET` (45 s). A failed fetch or push whose text names a refused login (`Authentication failed`, `Permission denied (publickey)`, `denied to`, HTTP 401/403, `terminal prompts disabled`, `repository not found`; looked for in the whole text, not only its useless last line) ends with status `auth` and the warning `auth: the repo refused the login (<line>); check the deploy key or the credentials of this machine`, not `offline`; `add-device` and `remove-device` stop with `sync first (auth)`. `cli.py` still ends `lm sync` with exit 1 only for `conflict`/`warn`: `auth` should join that list (a refused login is not cured by waiting; not done here). `init` and `join` end a timeout of git with a message (`cannot reach the repo: timed out after 45 s`, `cannot fetch the repo: ...`) and a refused login with `the repo refused the login`, never with a traceback.
- **`_commit` fails closed.** What is staged is listed by `git diff --cached --raw -z` and read BY OBJECT ID (`cat-file --batch-check` for the size, `--batch` for the content), whoever staged it. Refused, unstaged and named in a WARN (the rest goes through): a name with a line break, CR or invalid UTF-8; anything on the never-list (`.env`, `.key`, `system/` ...); a nested repo; a blob that cannot be read, is no blob, is missing or is over 5 MB (also one that grew after the size check); a file with a whole conflict block (`<<<<<<<` ... `=======` ... `>>>>>>>`); a file holding a value of a local secret (`tools.secret_masker`). An `.age` file passes unread only when it starts with the age header (`age-encryption.org/v1` and a line break); any other file with that name is checked like every file (conflict markers, secret values, size). A deletion passes. A tree with unmerged entries commits nothing. If a refused file cannot be taken out of the index, nothing is committed.
- **Hash rule (`reconcile`).** L = local `.env`, R = the repo's `.age` decrypted, S = last agreed. Both files: L==R agreed; L==S remote changed, `.env` is rewritten; R==S local changed, becomes `.age` (it waits while no recipient list is usable); anything else (or no S): CONFLICT. Only an `.age` (L missing): no S = a secret another instance made, written here; R==S = deleted here, so the `.age` is deleted and committed; otherwise CONFLICT (deleted here, changed in the repo). Only an `.env` (no `.age`): no S, or the `.age` is still in HEAD or in `origin/main` = new, lost here or made again after a local deletion: encrypted; otherwise (S set, the repo dropped it) L==S deletes the `.env`, else CONFLICT (changed here, deleted in the repo). S of a secret deleted here stays until the deletion is pushed (`_mark_synced` then drops what is gone on both sides), so a change that arrives meanwhile is a conflict. A conflict overwrites nothing, shows as WARN in the checklist and `lm sync status` with its kind (`why`: both / deleted_here / deleted_there), and is settled with `lm sync resolve <name/account> --keep local|remote` (deleting is a side too). Not a recipient: the local `.env` stays, warning "cannot be decrypted". S is set after a push and when L==R.
- **Remove-device.** Per secret `sync-secrets.json` remembers the hash of the `.age` this instance wrote and the fingerprint of the list it was made for; after every pull `rewrap` makes an `.age` of ours that was made for another list again (content unchanged); someone else's `.age` is left to its writer (otherwise two instances would rewrite each other's files for ever), except an `.age` a conflict took from the repo's side (once). `remove-device <name>` needs this instance in a valid list, changes the list with the lock held, drops the name and its confirmation, makes all secrets again, then `_settle`: push, `rewrap(foreign=True)` (every `.age` this instance can open, whoever wrote it; one it cannot judge is named as not checked), push again, up to four rounds; it says `removed` only when nothing is left and everything is pushed; otherwise it raises and the same command finishes the job (`status` shows REMOVING). Unpushed commits are squashed before a push (see `run`), so no version made for the old list goes up beside the rewrapped one. It ends by saying FIRST to take the device's access to the repo away (delete its deploy key at the git host: until then it can read everything pushed from now on), then it lists the secrets to change: every secret in the tree after the last pull (also what another instance wrote for the device before it pulled the removal) and every secret that has an `.age` anywhere in the history (`deleted since, but still in the history`). `add-device` changes the list under the lock too, does not take another key under an existing name and does not list a key twice.
- **Join is all or nothing.** `join` first checks for a file where the repo has a folder (or the reverse) and stops before it moves anything; the recipient list is asked before anything moves; a local file the repo also has: a different one goes to `<file>.lokal` (a free name), an identical one is parked in `.lm-join-*` and written again by the checkout; any failure or Ctrl+C puts every file back, removes the files and folders the checkout made, restores the instance files it wrote and removes the `.git` (read-only object files included): the tree is exactly as before.
- **Commands.** `lm sync` (= `run`), `status` (own key fingerprint, recipients with confirmation, RECIPIENTS warnings, REMOVING, CONFLICT; the `last sync` line says `(ok, 1 commit not pushed)` when a commit waits for its push), `init <url> [--machine N]` (remote must be empty; creates key pair, first recipient, confirms itself, encrypts existing `.env`, first commit, push), `join <url>`, `add-device <name> <age1...>`, `remove-device <name>`, `approve <name> [fingerprint]`, `resolve`. Errors are `SyncError(ValueError)`.
- **Processes and threads (top level only: `LM_DEPTH` 0, else nothing).** `_bg` threads are registered; an atexit hook `_finish` (20 s in all, minus what `session_end` waited; it starts no thread) drops a debounce that is not yet due and joins them, so a process end does not cut a run off and leave `sync.lock` or an unfinished push behind (cli.py and the TUI call nothing). The lock holds the owner's pid: a lock of a dead process is taken over at once (Windows: `OpenProcess`, never `os.kill`), a lock of a live one or of this process blocks, an unreadable one waits for `LOCK_STALE` (10 min). `start_pull(home)` (one background pull+push per process: `cli._start`, `Orbit.on_mount`; the boot checklist line `sync` awaits it up to 8 s via `checks.check_sync(home, pull=True)`; `lm check` only reads the last result), `after_turn(home)` (end of `Session.send`: commit+push in a thread, at most once per 30 s, one timer for a later change), `session_end(home, wait)` (end of `lm run` / `lm chat` and `Orbit.action_quit`: waits for a running sync, then commits and pushes, at most `wait` seconds), `tick(home)` (Orbit timer every 5 min). Nothing blocks the TUI.
- **Checklist line.** `check_lines`: a text conflict (`conflict, pull aborted ...` with the file names), a skipped run, offline, open conflicts, an invalid recipient list, unconfirmed devices and every other warning are WARN lines; it says ok only when there is nothing to say. The ok line, the offline line and the auth line (`auth: the repo refused the login ...`, a WARN) add `1 commit not pushed` when a commit waits for its push, so a plain `ok` never hides one.
- **Machine-bound content.** `Server.machine` and `Server.local` (= `machine` equals this instance's name; `host: local` still counts while no `machine:` is set and sets `legacy_local`); `Trigger.machine`; `tools/triggers/apply.py` installs a trigger only where `machine:` matches, or (field missing) where `always_on` is set in `local.md`; with no instance name it installs all as before, except `run: sync`. A trigger with `run: sync` or `run: check` (and no `agent`/`task`) runs `<tree>/system/lm sync|check` (crontab line, `schtasks` task); nothing else is allowed in `run`. A trigger like `machine: homeserver`, `*/15 * * * *`, `run: sync` is a 15-minute server sync; none is shipped (a fresh tree has the switched-off `example-weekly`). `sync.config_warnings` (shown as `sync` lines of `lm check` in a sync repo): legacy `host: local`, triggers without `machine:`.
- **Tests: `tests/test_sync.py`** (units + two or three temporary trees with a local bare repo, real child processes for the exit behaviour; slow, about 15 minutes because of git on Windows) and `tests/test_trigger_run.py`. Not done here: the rollout of the plan.

- **Interjections (interject.py, `Session.interject`).** A message of the user while a turn runs does not wait for the turn to end. `Session.interject(text) -> Item | None` puts it in `Session.inbox` (None = not taken: no turn running, read only, or `interject.MAX_OPEN` = 3 are open already; the caller then sends or queues it the normal way). The running turn reads it at the next transition and answers it in the same turn: `stream_loop` appends one user message (`Message.origin == "interject"`, text framed by `interject.frame`: who wrote it, "answer in one or two sentences, then adapt the work in progress, do not start over"; their words sit in `<interjection from="the user" id=n>` with `<` escaped, `interject.parse` reads them back) after the tool results of a turn, and also instead of ending a turn that would otherwise end (the loop goes on with a further model call). `Interjected(id, text, parent, agent)` is the event that says it was read (logged as `interjected`, the message is in events.jsonl and resumes). No on_prompt hook runs for it. Unread ones (turn stopped, failed, paused, or they came in after the last check) stay in the inbox; `Session.send` moves them to `Session.leftover` when it ends, `take_leftover()` hands them to the UI, which queues them again in front of its queue. Tool output cannot pass for an interjection: `Dispatcher.call` defuses `<interjection` tags in every result (`interject.neutralize`).
  - *Providers.* API providers (`owns_loop` False): the loop does the above; `anthropic_api.to_api_messages` puts the user message into the same user turn as the tool results (a text block after the `tool_result` blocks). `claude_sdk`: the SDK has streaming input (`ClaudeSDKClient.query` while a response streams), but where the CLI inserts such a message and how many `ResultMessage`s it then sends cannot be checked offline, so it is not used. All tools of that provider are Lightmind's own (built-in CLI tools are off), so every tool transition passes the MCP handler: it calls `Dispatcher.deliver()`, which takes the open messages, puts the framed text as an extra text block on the tool result and emits `Interjected` on the turn's event queue; the loop records the user message after the assistant message for a replay. A message that arrives during a model call without tools is read when the turn would end (the loop continues with a new `turn()`).
  - *Long work stays answerable.* `Dispatcher.call_watched` (used by the loop and the SDK handler instead of `call`): for `bash`, `spawn` and external tools, once a message is open (or arrives while the call runs) the call gets `interject.GRACE` (2 s) to end by itself, then it is detached: it keeps running as a job (`Dispatcher.jobs`, `job-1`...), the model gets `[bash is still running as job-1 ...; it was not stopped]` plus the message at once. The built-in tool `job` follows it: `status` (all jobs; a finished one's output comes once), `wait id [timeout]` (up to `interject.WAIT_MAX` 600 s; ends at once when a message is open or arrives, the job goes on), `cancel id`. Jobs end with the turn, but a turn is not allowed to end silently on one: when the model would end its turn while a job runs, the loop appends a harness note (`Message.origin == "harness"`, not shown by UIs: "ending the turn stops it, wait with `job wait` or `job cancel`") and goes on, up to `interject.MAX_HOLDS` (3) times in a row; after that `stream_loop` stops the job (the process tree is killed), says so in a `Notice("warning", "stopped with the turn: ...")` and logs a `jobs` event. Rounds that only call `job` do not count against `max_turns` (for `claude_sdk` the CLI's own turn limit still counts every call). A message in the last allowed turn is not fed (it would never be answered): it goes to the leftover. A detached foreground `spawn` is owned by the job list (not cancelled at the end of a model call). `ask` and the quick built-ins are never detached.
  - *Sub-agents.* Each sub-agent has an `Inbox` of its own (`source` "the main agent", registered in `SpawnCtx.shared["inboxes"]` with its starter while it works) that its `stream_loop` reads the same way. The built-in tool `relay(to, text)` (`to`: sub-agent id, name or `all`) puts a message there, only into the inboxes of sub-agents the calling agent started itself (no siblings, no grandchildren); the sub-agent is told it comes from the main agent, not from the user, and to mention what it changed. The main agent's interjection frame names the sub-agents that are working, so it can decide what to pass on. `Interjected` of a sub-agent carries `parent` and `agent`.
  - *TUI.* While a turn runs, a plain line (no slash words, no skill) is an interjection when no earlier message waits in the queue: its block shows `interjection · read at the next step`, then `interjection · read by the agent` when `Interjected` arrives; the status line counts `N interjected`. The fourth open one and everything after it is a normal queued message (`queued`). Esc takes unread interjections and the queue back into the input and stops the turn; after a failed or stopped turn the unread ones become queued messages. A resumed chat shows interjections as `You` lines.
  - *serve.* `send` while a turn runs no longer fails (a line with slash words or a skill is queued raw and prepared when the turn has ended well, as in the TUI): the answer data is `{interject: "i<n>", state: "pending"}` (read at the next step) or `{interject: "q<n>", state: "queued"}` (in line behind the turn). Event `interject {id, state, text}` with `state` pending | delivered (text = their words; with `parent`/`agent` set: the main agent's relayed message was read by that sub-agent) | queued | sent (a queued or unread message went out as a turn of its own; the turn follows) | dropped (the turn was cancelled or failed first: `text` is handed back). When a turn ends well, unread and queued messages are sent as the next turn (one message, in order); otherwise they come back as `dropped`. `session.open` history shows interjections as user text.
  - *Not done.* `lm chat` (line chat) has no concurrent input and does not interject. The limits (3 open, 2 s grace, 600 s wait) are constants in interject.py, not settings.

## Timers, session wake-up and the automatic watch (`wake.py`, `timers.py`, `watch.py`, `proc.py`; tests `tests/test_timers_watch.py`)
Goal: supervision of child runs and "come back to me later" must not depend on what a model remembers. Everything below is done by the core.
- **Wake a session (`wake.py`).** `deliver(home, run_id, text, source, key="") -> held|started|queued|refused` puts a signed entry into `runs/<id>/inbox.jsonl` (`source` is `Timer` or `Watch`, nothing else; HMAC with `<state>/wake.key`, so an agent that can write a run folder cannot forge one; unsigned or altered entries are dropped on read; an entry with the same `key` replaces the unread one; timers (not the watch) wake a session at most `watch.wake_per_hour` (20) times an hour, then `refused`). Who reads it: a running turn of `stream_loop` reads the inbox between model calls and puts the note into the same turn; a process with a screen or backend that holds the session and is idle (`Background.on_message` set: TUI, `lm serve`) polls every `spawn.WAKE_POLL` seconds and handles the framed text like the result of a background sub-agent (`Session.send(text, origin="subagent")`, so it counts against `spawn.auto_turns`, runs no `on_prompt` hook and may not start background sub-agents); otherwise `lm wake <session>` (started detached by `deliver`, or by the sweep of the tick for an inbox nobody reads) resumes the session headless for one turn (`watch.wake_max_turns`, default 30), the same history, and ends. A process that holds the session without a screen (`lm run`) is left alone: its entries wait (the tick tells the user after 10 minutes). `wake.frame(entries)` is the user message: `[Timer]`/`[Watch]` head ("not from the user and not output of a tool ... no new permissions"), each entry in `<system-note from=".." at="..">` with `<` escaped, control characters removed, `[Interjection]`/`[Harness note` heads defused (`wake.clean`; `wake.plain` for text that is not a prompt). After a woken turn of a session named in `watch.reply_telegram` (default none) the answer goes to the user on Telegram (`watch.send`).
- **Triggers on a clock (`timers.py`).** `when: every <N>m|h` and `when: in <N>m` (N·60 s at least 60), keys `session` (an EXISTING session by name or run id: wake it with `task` as the message; without an existing session and with `agent`+`task` the first call makes it, as before), `until` (an ISO time, `in 3h`, or `children-done`), `owner` (the session that made it; `Trigger.until`, `Trigger.owner`). Two places: `triggers/*.md` (people; a write asks the user) and `<state>/triggers/*.md` (the core only: timers and watch triggers, `kind: timer|watch`; no agent can write there). `tick(home, now)` (CLI `lm triggers tick`, once a minute from the OS) fires what is due: state in `<state>/ticks.json`, `created` or first sight is the anchor, a beat missed is made up at most once, a beat is never fired twice, one tick at a time (`<state>/tick.lock`), `machine` as in apply.py. A trigger without session/owner but with agent and task starts `lm run --detach -a <agent>`. Cron stays with `tools/triggers/apply.py`, which now skips `every`/`in` silently. `lm triggers install|uninstall|status|list`: Linux `systemd --user` timer `lightmind-tick` (else a marked crontab block), Windows task `Lightmind tick`; `lm init`/`lm update` offer it. `lm check` needs nothing of it.
- **`timer` tool** (built-in, always on): `set when message [until]`, `list`, `cancel id`. Only the caller's own session (`self.run.run.id`; there is no target argument), min distance 1 min, at most 20 per session, horizon 30 days, a repeating timer without `until` ends after 24 h, a message is at most 1000 characters. It writes through `timers.set_timer`, not as a file write of the agent, so `triggers/**` stays protected and no question is asked.
- **Children book and watch (`watch.py`).** `lm run --detach` with `LM_PARENT` set calls `watch.register_child`: entry in the book `<state>/watch/<parent>.book.json` (a copy for reading is `runs/<parent>/children.json`; the copy is never read back; registered only with `LM_PARENT_SIG`, an HMAC of the parent id that the core puts into the tool environment, and only when the child's own meta names that parent) (`id, title, start, status running|paused|handover|done|failed|abandoned, restarts, verdict, verdict_at, action`) and one trigger `watch-<parent>` in the state folder: `every <watch.every> until children-done`, `kind: watch`. Each beat `cycle(home, parent)`: per open child a verdict (`ok|slow|stalled|off_track|dead|done|failed|paused|handover`): the core's own facts decide end states (a running run without a process is `dead`, see `runs.reap_dead`); a run that lives is asked about its course by the check tool of the tree, else the built-in `script_check` (process, status, time since the last event (`watch.stall_minutes`, 30), errors among the last events); the tool's answer never ends or restarts a run. Healing: `dead`, `paused` for `max_turns`/429/rate limit, `handover` -> `lm run --continue <id>` as its own process (same session, the handover text carries on), at most `watch.max_restarts` (3) per child (counted in `<state>/watch/<parent>.json`, not in the run folder), waiting 1, 2, 4 min before each; other pauses (budget, interrupted) and `failed` are only reported; `off_track` gives a message with the suggestion, no restart. `poll` (every minute, no model, no check tool) brings a changed child state forward to the next minute. One wake message per beat lists all children (`watch.wake_when_ok`, true). When the last child is closed the watch trigger ends and "All N sub-runs are finished" goes out once.
- **Check tool interface** (tree tool `tools/watch/watch.py`, or the command in `watch.checker`): `<checker> check --run <run-id> [--brief <file>] --json`, working directory = tree root, one JSON line on stdout `{"run","verdict","reason","evidence":[..],"method":"<word>|script" (one short lowercase word, e.g. `model`; anything else counts as `script`),"suggest":"none|nudge|restart|continue|ask"}`, exit 0 when valid; anything else (missing, exit != 0, bad JSON, unknown verdict) -> the core's own script check. Its text is untrusted (cleaned, bounded).
- **Dead runs.** `runs.reap_dead(home, id)`: status `running` with no live process (no session lock holder, pid gone; no pid for more than `STARTUP_GRACE`) -> status `failed`, `exit_reason` `process died` or `never started` (`runs.DEAD_REASONS`, `runs.is_dead`), end marker in `log.md`. Called by `run_result` (`lm wait`), `list_runs`, `show_run` and the watch. (Decision: no new status value `dead`, so nothing that reads `RunStatus` changes.)
- **Detached start (`proc.py`).** `popen_detached` (used by `lm run --detach`, `lm wake`, the restarts): Linux with a systemd user manager -> `systemd-run --user --scope --collect -- <cmd>` (probed once; `LM_NO_SCOPE=1` turns it off), else `start_new_session`; Windows a hidden console.
- **Messages to the user (`watch.notify`).** `watch.notify` = `telegram|ntfy|both|off` (default both: every channel that is set up; Telegram when `tools/telegram/` exists, falling back to ntfy). Events: dead/failed/off_track child, restart, gave up, all done; each event key goes out once. Telegram is `watch.telegram_command` (default `uv run tools/telegram/telegram.py send`) with the text on stdin (or in place of `{text}`); ntfy is `uv run tools/ntfy/notify.py <text> --title Lightmind`. No shell is involved.
- **State block.** `Session._state_info` adds `sub-runs:` (the open children, one line each, at most 8) whenever the book has open children; the block is rebuilt when the list changed.
- **Settings.** `config.md` `watch:` `every` (5m..2h), `max_restarts` (0..10), `notify`; the rest in `lightmind.md` `watch:` (`stall_minutes`, `wake_when_ok`, `wake_per_hour`, `wake_max_turns`, `reply_telegram`, `telegram_command`, `checker`).
